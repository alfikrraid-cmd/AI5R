## Frozen Decisions

- **Governance precedence is one-directional and locked:** Blueprint → ADR → Engineering Standard → MWO → Source Code. No document type may be revised merely because source code currently does something different (`ADR-000` §5).
- **Foundation v1.0 and Engineering Standard v1.0 are locked.** No MWO in the Engineering Knowledge Acquisition epic has modified either.
- **Canonical table shape is fixed:** `TEXT` primary key, `created_at`/`updated_at TIMESTAMP DEFAULT NOW()`, closed-set fields enforced by `CHECK` constraints (never a code branch). Established by `BP-SEAL`/`seal_registry`, reused by every table since.
- **Engineering Acquisition Pattern (`ADR-004`) is mandatory** for every Acquisition Object type: Acquisition Object → Metadata → Classification → Acquisition Job. PDF and Engineering Media conform; Workbook does not yet (tracked in `TECHNICAL_DEBT.md`, retrofit specified in `MWO-LTSA-040C-R1`, not implemented).
- **`AI5R-SDK/KNOWLEDGE` is frozen, AI5R-platform-level, and unrelated to LTSA-BRAIN's `knowledge_source_registry`** — same name, different artifact, never integrated, never modified by any LTSA MWO (`MWO-LTSA-040A` Architecture Decision items 1–2).
- **The Acquisition Layer performs no OCR, text/table/image extraction, AI reasoning, recommendation, or engineering-object manufacturing.** Every field on every Acquisition Object/Metadata/Classification/Acquisition Job table is caller-supplied. Extraction and analysis are explicitly deferred to future MWOs (040F, 046–049, 050–053).
- **No Delete operation exists on any immutable registry** (`knowledge_source_registry`, `workbook`, `pdf_document`, `engineering_media`, and their respective Metadata/Classification tables) — originals must never be removable via their own acquisition workflows.
- **`PRODUCTS/LTSA-BRAIN/RELEASE/*` is not a canonical schema source.** It is a stub artifact produced by an unrelated, unauthorized test side effect (`RCA-001`) — `CANONICAL_SCHEMA.sql` and each BUILD-PACK's own `SCHEMAS/*.schema.json` remain the only canonical release-adjacent artifacts until a Chief-Architect-level decision changes this.
- **Documentation is part of the implementation** (`DOCUMENTATION_CONTRACT.md`, integrated into `ENGINEERING/AI5R_ENGINEERING_STANDARD_v1.0.md` §18). No MWO is Commit Ready without it.
- **UMC-001 (Universal Manufacturing Contract) is the platform-wide, canonical nine-stage contract every Manufacturing Pipeline must implement** (`AI5R-SDK/FACTORY/CORE/universal_manufacturing_contract.py`, established `MWO-LTSA-048`). Canonical specification now standalone at `AI5R-SDK/PLATFORM/MANUFACTURING/UMC-001-Universal-Manufacturing-Contract.md`, mirroring UMR-001's own Platform Artifact placement; `MWO-LTSA-048` remains its unmoved origin/audit record. Seven stages reuse existing `AI5R-SDK/FACTORY` primitives unchanged (`ManufacturingOrder`, `ManufacturingContext`, `BaseManufacturingStation.validate`, `ManufacturingObject`, `ManufacturingEvent`/`ManufacturingEventBus`, `ManufacturingResult`, `ManufacturingPipeline`/`Runtime`/`Engine`). Two — Identity Resolution and Relationship Resolution — are deliberately platform interfaces only (`AI5R-SDK/FACTORY/RESOLUTION/{identity_resolver,relationship_resolver}.py`), with no concrete resolution logic; each Factory Pack (LTSA-BRAIN first) implements them against its own domain. This is a platform-wide artifact, not an LTSA-BRAIN-only one, despite its `MWO-LTSA-048` identifier (retained by explicit Chief Architect decision).
- **Column Mapping (`mapping_profile`/`column_mapping`, MWO-LTSA-040C) is one Factory Pack's own input-normalization capability, not the Manufacturing Contract itself** — a category distinction corrected during `MWO-LTSA-048`'s own review (Rev. 1 → Rev. 2), recorded here so it is not re-confused in future work.
- **UMR-001 (Universal Manufacturing Runtime) is `AI5R-SDK/FACTORY/FOUNDATION.ManufacturingRuntime`, extended, not a new runtime** (`MWO-LTSA-049`). Chain A (`ManufacturingRuntime`/`FactoryOrchestrator`/`FactoryCompiler`/`ManufacturingPipeline`) is the sole platform runtime executing UMC-001. Chain B (`ManufacturingEngine`) is the **Release Engine**, Chain C (`ManufacturingService`) is the **Factory Generator**, Chain D (`FactoryRuntime`) is the **Project Generator** — each retains its own separate, legitimate purpose and none is deprecated or merged. No second Runtime exists or may be created without a new Chief Architect decision.
- **`FactoryPack` is a first-class Runtime citizen as of UMR-001**: validated the same way a `ManufacturingOrder` is, threaded through `ManufacturingContext.metadata`, and reflected in the runtime's own result. `IdentityResolver`/`RelationshipResolver` remain interfaces only, exposed as pluggable hooks via context metadata — no concrete resolution logic exists in the platform; each Factory Pack (LTSA-BRAIN first) supplies its own.
- **`CORE.ManufacturingEvent` and `FOUNDATION.ManufacturingEvent` are two different, incompatible classes sharing one name** (discovered `MWO-LTSA-049`) — a pre-existing Canonical Rule violation, not remediated. Per explicit Chief Architect directive this is **not** ordinary Technical Debt: it is tracked as `ENGINEERING/MWO/ARCH-REVIEW-002-Canonical-ManufacturingEvent.md`, Status **DEFERRED**, Target **After LTSA v1.0** (`TECHNICAL_DEBT.md`'s `TD-006` is now only a pointer to this record). UMR-001's own extensions use exclusively the `FOUNDATION` variant to avoid deepening the conflict. No resolution may be decided outside that Architecture Review.
- **`AI5R-SDK/PLATFORM/MANUFACTURING/UMR-001-Universal-Manufacturing-Runtime-Specification.md` is the canonical UMR-001 specification** (relocated from `ENGINEERING/MWO/` under the Platform Artifact placement rule established by `MWO-PLATFORM-001-AI5R-Command-Language.md` — Engineering stores work, Platform stores artifacts) (established alongside `ARCH-REVIEW-002`, documentation-only, no implementation change) — covers Purpose, Responsibilities, Lifecycle, Manufacturing Request/Context, Validation, Identity/Relationship Resolution, Event Publication, Runtime Result, and FactoryPack Integration, grounded in the actual `MWO-LTSA-049` implementation. It explicitly records the accepted Stage 8 (`ManufacturingResult` expressibility) gap as a disclosed, accepted WARNING rather than closing it.
- **Five independent, structurally-convergent Worker implementations were found across `WORKFORCE`, `RUNTIME`, `ORGANIZATION`, `MANUFACTURING_CENTER`, and `DIGITAL_EMPLOYEE`** (`MWO-PLT-002` WP-000, elevated per explicit Chief Architect directive — not ordinary Technical Debt). Tracked in full at `ENGINEERING/MWO/ARCH-REVIEW-003-Canonical-Worker-Review.md`. Resolution: **`ADR-AR-003` — Option A' (Canonical Promotion Strategy)**, decided 2026-07-15 — `RUNTIME.EnterpriseWorker`/`Worker(Protocol)` is promoted to canonical (UWP-001), the other four are not migrated or retired immediately; a Compatibility Layer, then a gradual Migration Plan, then a Deprecation Strategy follow in that order, each requiring its own separate Implementation Approval. No implementation has begun.
- **`ADR-AR-003` establishes Canonical Promotion as AI5R's default platform-wide strategy whenever multiple implementations of the same platform concept are found**: promote the preferred implementation to canonical, maintain compatibility, migrate gradually, retire only after successful migration — no immediate replacement or destructive rewrite. First applied de facto to UMR-001 (`MWO-LTSA-049`), now formalized as policy via the Worker finding (`ARCH-REVIEW-003` §6). Applies as the default for future canonical-ambiguity findings unless a Chief Architect decision states otherwise for a specific case.
- **Canonical Worker Promotion (`MWO-PLT-003`, WP-001–WP-005, all approved) and its Worker Runtime follow-on research (`MWO-PLT-004`, WP-000, approved) are paused, not closed.** `EnterpriseWorker`/`Worker(Protocol)` remains the confirmed Canonical Worker; the Compatibility Specification (`MWO-PLT-003` WP-003) and its five open gaps (WP-005) stand as recorded. Findings from `MWO-PLT-004`'s Worker Runtime research are classified in `TECHNICAL_DEBT.md` as `TD-007` (`MissionRuntime` exception propagation on worker execution failure — HIGH PRIORITY) and `TD-008` (Worker status lifecycle/reservation/recovery/observability/mutual-exclusion gaps — DEFERRED). **Per explicit Chief Architect directive, Worker Runtime implementation does not resume unless a finding becomes a direct blocker for LTSA v1.0** — current objective is LTSA Manufacturing, not platform Worker Runtime hardening.
- **No canonical Installation object exists anywhere in the repository, confirmed by `MWO-LTSA-053` research — and none is to be invented speculatively.** Per explicit Chief Architect directive: any future Installation object must be derived from existing LTSA implementation (real schema/table precedent), not designed from first principles. `MWO-LTSA-053`'s own candidate shape (§1, by analogy to `asset_registry`/`work_order`/`seal_pump_compatibility`) is inference for research purposes only, not an approved design.
- **`AI5R-SDK/MANUFACTURING` and `AI5R-SDK/FACTORY` share class names (`ManufacturingOrder`, `ManufacturingObject`) between two structurally different, unrelated systems** — `AI5R-SDK/MANUFACTURING`'s own (`ManufacturingRecipe`/`DigitalFactory`/`ProductionLine`) manufactures organizational artifacts (Company/Department/Role); `AI5R-SDK/FACTORY`'s own is what `UMC-001`/`UMR-001` govern. Discovered during `MWO-LTSA-053` research. **Confirmed real by Chief Architect directive, but not resolved within that MWO** — tracked as `TECHNICAL_DEBT.md` `TD-009`, a future Architecture Review candidate, not yet elevated to its own review (contrast `TD-006`/`ARCH-REVIEW-002`, which was elevated). Do not conflate the two systems' same-named classes in any future work.
- **A Factory Pack's manufacturing station is a plain `FACTORY.CORE.manufacturing_station.BaseManufacturingStation` subclass, not an `ADR-003` Capability** — decided by explicit Chief Architect directive for `MWO-LTSA-050` WP-001 (Pump Factory Pack), resolving Open Question 6 from `MWO-LTSA-050` WP-000. Reason given: Manufacturing Station is a Factory concept; Capability and Manufacturing are separate architectural layers; UMC-001's own existing lifecycle must be reused, not a second execution model introduced. Applies as precedent to future Factory Packs (Seal, Maintenance, Installation) unless a Chief Architect decision states otherwise for a specific case.
- **`recipe.json` v1 — the minimal schema for `FactoryPack.recipe_path`** — decided by explicit Chief Architect directive for `MWO-LTSA-050` WP-001, resolving Open Question 2 from `MWO-LTSA-050` WP-000 (no `recipe.json` existed anywhere in the repository before this). Fields: `recipe_id`, `recipe_version`, `object_type`, `identity_key`, `relationship_keys`, `stations`. First instance: `PRODUCTS/LTSA-BRAIN/PUMP-FACTORY-PACK/recipe.json`. Treated as v1, minimum-only — not a general recipe execution framework; no loader/engine interprets it yet. Future Factory Packs shall reuse and extend this shape rather than invent a second one.
- **Pump is now the first real Factory Pack consumer of UMC-001/UMR-001** (`MWO-LTSA-050` WP-001): `PumpIdentityResolver` (Stage 4, matches `ltsa_pumps.tag_number`) and `PumpRelationshipResolver` (Stage 5, matches `seal_type` against `seal_registry.seal_name` → `seal_code`) are the platform's first concrete `IdentityResolver`/`RelationshipResolver` implementations. Both are read-only, take their reference data via constructor injection (no I/O of their own — consistent with every other `FACTORY.RESOLUTION`/`FACTORY.CORE` class), and live under `PRODUCTS/LTSA-BRAIN/PUMP-FACTORY-PACK/` (product layer), not `AI5R-SDK/FACTORY` (platform layer) — following the `PRODUCTS/LTSA-BRAIN/AI-ASSISTANT/` precedent for where product-specific Python code lives. No `AI5R-SDK/FACTORY` file was modified to build this.
